## The false-completion bug (2026-08-12) — read this before touching mutations
**Symptom:** Santiago told the bot two tasks were done; it replied "Marqué como hechas..." and the next morning's brief still listed them. Verified against the Task API: rows 503/506/507 were still `To-do`.

**Root cause:** every mutation depends on the model choosing to emit a tool call, and there was NO code-level check that a claim corresponded to a real write. Prompt rules against narrating-without-calling had failed three times (Jun, Jun-18, Aug). Yesterday's logs were unrecoverable (journald volatile, no `/var/log/journal`), so the mechanism could not be proven from logs — but it was reproduced empirically during the model test below.

**The lesson (do not relitigate):** when a behavior MUST happen, put it in code, not in the system prompt. Same conclusion as the all-done celebration.

**Fixes shipped:**
1. `melissa.js` — `MUTATING_TOOLS` / `toolFailed()` track whether a mutating tool actually ran AND succeeded. If the reply claims an action and none did, `GUARD_CORRECTION` is injected and the tool loop re-runs once; if the claim survives, the false text is replaced with an honest failure notice. `claimsMutation()` strips interrogative clauses so offers ("¿la marque como hecha?") are not treated as claims. A partial batch write (`⚠️ Solo N de M`) counts as a real mutation so the guard cannot overwrite a truthful partial-success reply.
2. `tasks-mcp.js` — `apiFetch` now fails on non-2xx instead of returning the body regardless of status; `update_tasks` reports per-task failures and no longer returns "✅" for an empty `updates` array or a field-less patch (**both were silent false successes**); a thrown fetch no longer rejects `Promise.all` and hides sibling outcomes.
3. Removed a hardcoded `TASK_API_SECRET` fallback from `tasks-mcp.js` (dead code — the bot always supplies it via env — but a live credential in readable source). Now exits 1 if unset. **The secret still needs rotating.**

**Gotcha worth keeping:** `\b` is a no-op next to accented letters in JS regex (`é` is not `\w`). The first guard regex silently failed to match "Marqué"/"eliminé"/"moví" — the literal failing string. Boundaries use `\p{L}` lookarounds with the `u` flag.

## Model choice (measured, not guessed)
Real API test 2026-08-12 on this prompt shape:

| model | effort | latency | tool call | out tokens (reasoning) |
|---|---|---|---|---|
| gpt-4.1-mini | — | 2756ms | ✅ | 10 (0) |
| gpt-5-mini | default | 2937ms | ✅ | 151 (128) |
| **gpt-5-mini** | **low** | **2631ms** | **✅** | **87 (64)** |
| gpt-5-mini | minimal | 1505ms | ❌ **NONE** | 46 (0) |

`reasoning_effort: "minimal"` **reproduced the exact narrate-without-calling bug**, so `chatCreate()` refuses to send it. All three per-turn completion calls route through `chatCreate()` so they cannot drift apart.

**Cost:** July was 3.81M input / 94.9K output — input-dominated ~40:1 because the full system prompt ships on every call. gpt-4.1-mini ≈ $1.67/mo; gpt-5-mini at `low` ≈ **$2.60/mo** (reasoning tokens bill as output, ~8× more). A same-token-count estimate wrongly suggests gpt-5-mini is cheaper — it is not.

## Architecture
Repo files:
- `melissa.js` -> deployed as `/opt/melissa/whatsapp-bot/whatsapp-bot.js`. Bot loop, onboarding, per-user routing/isolation, OpenAI tool orchestration (`chatCreate`), mutation-claim guard, cron briefs, SELFCHECK.
- `db.js` -> SQLite (`node:sqlite`) users + invite_codes + debts. Debts isolated by `WHERE user_id=?`.
- `sheets-mcp.js` -> Networking Google Sheet MCP (Santiago-only feature today).
- `categories.json` -> task categories.
- `ops/deploy-melissa.sh`, `ops/melissa-bot.service`, `ops/README.md` -> production runtime, version-controlled.

Server-only (**NOT in repo**, edit on VM): `/opt/melissa/.openclaw/skills/tasks-mcp.js` (Task Dashboard MCP) and `calendar-mcp.js` (Google Calendar/Gmail MCP). **Mirror any change to `/root/.openclaw/skills/*` for rollback parity** — and use `sudo test -f` to check those paths; an unprivileged `[ -f /root/... ]` silently returns false and will make you think the file is absent.

Load-bearing ideas:
- Task ownership = `[uid:CHATID]` tag inside the task title; Santiago's tasks are untagged. Reads filtered by `filterTaskOutput`; writes/deletes gated by `ownedTaskIdSet` (fail-closed).
- Brief markers (`🔴` priority, `🔜` tomorrow) come from tool output; the model preserves them, never invents them.
- Paths are env-parameterized (`DB_PATH`, `CFG_PATH`, `CATS_PATH`, `USAGE_LOG`, `PRIORITY_FILE`, `SKILLS_DIR`) with `/root` defaults; the systemd unit points them at `/opt/melissa`.
- `OPENAI_MODEL` is passed to tasks-mcp at spawn so `get_usage` prices against the model actually in use.

No build step. `npm install --omit=dev` only.

## Key decisions (do not relitigate)
- **Reliability guarantees live in code, not the system prompt.** Prompt-only fixes for hallucinated actions failed three times.
- **Never use `reasoning_effort: "minimal"`** — measured to break tool calling for this workload.
- **Deploy branch is `pause-morning-brief`**, not `main`. `deploy-melissa.sh` defaults to it.
- **Google multi-user (Calendar/Gmail) deliberately deferred.** The MCP servers boot with Santiago's single OAuth token, so enabling `calendar`/`email` for another user would expose his account. Needs per-user OAuth first. Do not flip those flags for invited users.
- **`tasks-mcp.js`/`calendar-mcp.js` are server-managed** by design (not shipped by the deploy script).
- **`RestrictSUIDSGID` omitted** from the unit: VM is systemd 239, that directive needs >=242.
