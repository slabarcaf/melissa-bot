## Shipped today

**1. Web ↔ Telegram account linking — built, deployed, verified**

The missing primitive: a dashboard account and a Telegram chat had no way to become the same person.
Six people had signed in with Google and landed on an empty dashboard because of it.

- Postgres `telegram_link_codes` (single use, 24 h, minting retires the previous unused code).
- `POST /api/telegram/link` — **cookie auth only.** The bot's shared secret must not be able to mint
  a code; if it could, holding that secret would let anyone claim any account.
- `POST /api/telegram/redeem` — **bot token only, and deliberately without the owner fallback the
  task routes have.** The chat id in the body is what is being granted access, so a fallback would
  hand the owner's tasks to whoever sent the command.
- Bot command `/link CODE`, handled **before** the authorization check because the sender is by
  definition not yet a registered chat. On success it creates the local record and runs the normal
  onboarding, since language, timezone and brief times live in the bot's own SQLite.
- `t.me/Melizion_bot?start=link_<CODE>` arrives as `/start link_…` and is rewritten to `/link`, so
  the web can offer one tappable link instead of asking someone to copy a code into a chat.

Verified against production, all five paths: valid, unknown, reused, expired, and a chat already
belonging to someone else (`chat_taken` — this is the one that matters; without it, redeeming from an
already-linked phone would move that chat's tasks to another account). The test linked and then
unlinked a real row and left the database as it found it.

## The thing to decide before writing more code

**Preferences live in two stores.** The web's `users` row in Postgres holds email, name,
`telegram_chat_id`, `tipo_options`. The bot's own SQLite holds language, timezone, brief times,
categories and feature flags. Linking joins the identities, not the settings.

The Settings panel in the mockup writes exactly the fields that are in the *bot's* store. So either
the panel talks to the bot's database, or those fields move to Postgres and the bot reads them from
the API. **The second is the right end state and it is the next real piece of work** — without it the
settings panel is either fake or duplicated.

## Traps worth not rediscovering

- **A commit whose author email is not a GitHub account will not deploy.** Vercel marks it `Blocked`,
  which reads like a usage limit rather than a config error, and the deployment can never be
  released — only superseded by a new commit with a valid author. Global git identity is now set to
  `207892885+slabarcaf@users.noreply.github.com`.
- **Vercel environment variables only apply on a rebuild.** `NEXT_PUBLIC_*` are inlined at build
  time; the server-side ones need a redeploy too.
- **A new deployment URL needs adding to the web OAuth client's authorized JavaScript origins**
  (`…-p82fvab9n0fkdou4nevr0na7k8q9jbs3`, Google Cloud project `<gcp-project-number>`). The *other* client in
  that project is the bot's Google access — do not touch it.
- **The Google sign-in button is the fragile part of any redesign.** Its effect bails if the ref is
  null and does not re-run when the div appears later, so the `useRef` and the effect must live in
  the same component that renders it. Google injects an iframe; it cannot be styled.
- `page.tsx` is still 1,733 lines. The split is planned but not started.
