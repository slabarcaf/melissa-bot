## Lo que hay que saber antes de tocar

**El admin sale de `ADMIN_EMAILS`**, y si no está definida cae a
`DEFAULT_OWNER_EMAIL`. No hay que configurar nada en Vercel.

**La API de admin rechaza `OPENCLAW_API_SECRET` a propósito.** Ese token resuelve
a la cuenta del dueño, y el dueño es el admin: aceptarlo convertiría una cadena
del `config.json` del bot en una llave al resumen de todas las cuentas.

**Eliminar una cuenta borra sus tareas primero, en la misma transacción.**
`tasks.user_id` es `ON DELETE SET NULL` y `ensureOwnerUserAndBackfill` barre las
huérfanas hacia el dueño en el siguiente arranque. Es la trampa de septiembre.

**No enfoques con `requestAnimationFrame`.** No dispara en una página que no está
componiendo cuadros. La paleta se abría sin foco por eso.

**La interfaz está fijada en español.** Seguía a `navigator.language` mientras
todas las cadenas de la aplicación son español fijo, así que un navegador en
inglés veía media traducción. `categoryLabel` sigue traduciendo: cuando se
extraigan las cadenas, vuelve a ser una preferencia.

**No corras `npm run build` con `next dev` levantado.** Comparten `.next` y el
build de producción pisa los chunks del dev: aparece `Cannot find module './276.js'`
y 500 en todo. Se arregla con `rm -rf .next`.

## Adenda — 2026-09-06: las preferencias viven en Postgres

**Desplegado y verificado de punta a punta.**

Idioma, zona horaria, horarios de briefs y categorías (con sus keywords) son
columnas de `users` en Postgres. `/api/user/preferences` responde a una sesión
del navegador **o** al token del bot más el chat id, las dos puertas que ya tenía
`/api/tasks`.

**`melissa.db` sigue existiendo, como espejo.** Es deliberado: cada lectura en
`melissa.js` es síncrona, incluidas las de los crons, y un brief que no sale
porque falló una consulta HTTP es peor que una preferencia quince minutos
desactualizada. Las escrituras van a la API primero y se espejan después, así que
si la API rechaza, el espejo conserva el valor viejo y los dos nunca discrepan en
la dirección en que el bot cree algo que nunca se guardó.

**Lo que la migración encontró.** Los dos almacenes no estaban solo duplicados:
se contradecían. La lista web de the second user eran cinco identificadores en inglés — Job,
Others, Finances, Household, Sport — que **no aparecían en ninguna de sus
tareas**, mientras sus tareas reales usaban la lista española que eligió por
Telegram. La de Santiago no tenía cuatro categorías que usa a diario. La regla
que se aplicó: *lo que eligieron en Telegram ∪ lo que sus tareas de verdad usan*,
y el script se niega a correr si eso dejaría fuera una categoría con tareas
detrás. the second user 6 → 5, Santiago 8 → 13. El script quedó en
`scripts/migrate-preferences-from-bot.mjs` del repo del dashboard.

**Se cerró el fallback del dueño.** Era inalcanzable para cualquiera real, pero
mover las preferencias aquí lo volvió urgente: con el fallback puesto, un usuario
de Telegram sin cuenta web terminando su onboarding habría escrito su idioma, su
zona horaria y sus horarios **sobre la cuenta de Santiago**. Ahora un chat sin
vincular recibe 401.

**Trampas nuevas, escritas en `CLAUDE.md`:** no escribir una preferencia directo
en SQLite (el siguiente sync la pisa), `categories.json` es solo el respaldo
cuando el espejo está vacío, y todo `require()` nuevo hay que agregarlo a
`ops/deploy-melissa.sh` — `prefs.js` no estaba y el servicio habría reiniciado a
un bucle de `MODULE_NOT_FOUND` con el proceso viejo ya muerto. El script ahora
aborta antes de tocar systemd si falta un archivo.

## Adenda — 2026-09-10: el health check nocturno

Reportó cuatro fallas y **todas eran una sola causa**: mandaba el token sin
`X-Telegram-Chat-Id`, y desde el 2026-09-06 la API rechaza una petición del bot
que no nombra a nadie. El chequeo tenía razón en gritar.

Pero arreglar solo la cabecera habría dejado tres chequeos que ya no miden nada:

- **"missing due dates" — retirado.** `due_date_next_step` es `NOT NULL` y tiene
  cero nulos: no podía dispararse. Y el miedo que codificaba —una tarea invisible
  a todo filtro de fecha— también se fue: el dashboard nuevo tiene sección "Sin
  fecha".
- **"priority flags" — retirado.** La prioridad es `tasks.is_priority` desde el
  2026-09-01. El archivo que leía es una foto congelada del 2026-08-28.
- **"status integrity" tenía una falsa alarma latente:** a su lista de estados
  válidos le faltaba `On-going`, que el diálogo de edición ofrece. Llevaba
  semanas en verde por suerte, no por estar bien.

**Dos chequeos nuevos.** El de Task API ahora corre **por usuario**: un ping
anónimo no puede ver la falla que importa desde que se cerró el fallback —que a
un usuario se le rompa el vínculo mientras el resto sigue funcionando. Y si el
401 es de todos dice "revisa task_api_secret", porque mandar a alguien a buscar
un problema de vinculación cuando el token está mal cuesta una hora.

El de **espejo de preferencias** cubre el modo de falla que introduje la semana
pasada: si el sync falla en silencio, el bot corre con valores viejos —briefs a
la hora equivocada— y nada más en el sistema se entera.

**La regla que quedó escrita en `CLAUDE.md`:** un chequeo que no puede determinar
su respuesta reporta falla, nunca aprobación.

Verificado contra producción levantando la función desde el fuente y
ejecutándola: pasa limpio hoy, y **falla como debe** con token malo, con espejo
desviado y con un chat sin vincular. Las pruebas destructivas corrieron sobre una
copia de `melissa.db`; la real nunca se tocó.
